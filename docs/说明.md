## 3. 选择相机

### 怎么调视角（速查）

**改哪个文件**：`configs/cameras.yaml` 是训练/转换真正用的那份（两个相机 `global` + `wrist`）。
`configs/cameras_candidates.yaml` 只是备选菜单，随便加、随便试，不影响训练。

**三个旋钮**（末端相机，都在 `site: end_effector` 坐标系里）：

| 旋钮 | 本意 | 怎么调 |
|---|---|---|
| `eye` | 相机在**哪** | `eye[2]` 越负 = 相机越往法兰后方退、视野越干净；`eye[0]` = 横向跨过两指；`eye[1]` = 沿两指张开方向 |
| `target` | 相机**看哪** | 只决定方向。想看得更"斜"，就把 `target` 往某个方向挪；`target[2]` 只影响视线是否平行于夹爪轴 |
| `roll` | 画面**转多少** | `0` = 两指连线竖直，`±90` = 水平（常规手柄视角）。纯自转，不花遮挡代价 |

**三步流程**：

```bash
# 1) 扫一遍候选（只传想扫的轴，没传的沿用配置里的值），出对比图 + 数值表
python scripts/sweep_camera.py --camera wrist --eye-z -0.51 -0.41 -0.31 -0.21

# 2) 看 previews/camera_sweep/sweep_wrist.png，并照抄终端最后打印的 YAML 片段
#    （脚本会把一组参数打印成可直接粘贴的 YAML 片段）

# 3) 把选中的值写回 configs/cameras.yaml，然后确认整个训练配置的两个视角
python scripts/preview_cameras.py --camera-config configs/cameras.yaml \
  --dataset-id D4RL/kitchen/partial-v2 --episode 0 --output previews/training_cameras --columns 5
```

`preview_cameras.py` 的列是**任务完成时刻**（reset + 每个任务刚完成），所以一眼能看出
"到夹爪靠近物体时还能看见目标吗"；`sweep_camera.py` 的列是**均匀采样帧**，
数值更适合横向比较。两个工具的口径不同，数字不要互相套用。

**三条硬规则**（否则会拍废画面）：

1. **`eye[2]` 必须 <= −0.18 左右**。手掌网格在 EE 系里占据 z ≈ −0.18 ~ +0.03，
   相机进到里面就会把网格的黑色内表面渲染在画面正中（就是那团"黑球"）。
   `wrist_inside_mesh_BAD` 就是反例。
2. **别随便给 `eye` 加横向分量**。`eye[0]`/`eye[1]` 非零 = 相机离开夹爪中线，
   好处是能斜着看，代价是夹爪很快被自己的手挡住（实测从遮挡 0.005 涨到 0.1–0.27）。
3. **改了相机就要重转数据集**。画面内容变了，`kitchen-to-lerobot` 必须重跑；
   但**相机键名（`global` / `wrist`）不能改**，它写进了 checkpoint 的 `input_features`。

**注意**：`configs/cameras.yaml` 里的 `wrist` 是已经选定的默认配置；候选表 `wrist_deep` 是
同一个位姿再往后退 20 cm 的版本（`eye = [0.0, 0.0, -0.41]`）。

---

相机全部在 `configs/cameras.yaml` 里配置，改 YAML 不需要改代码。
**YAML 里的键名会直接成为 LeRobot 特征名 `observation.images.<键名>`**，
并且写进 checkpoint——训练开始后不能再改名。

先在候选集上出对比图再决定：

```bash
python scripts/preview_cameras.py \
  --camera-config configs/cameras_candidates.yaml \
  --dataset-id D4RL/kitchen/partial-v2 --episode 0 \
  --output previews/camera_candidates --columns 5
```

输出 `previews/camera_candidates/sheet.png`：每行一个候选相机，每列一个关键时刻
（reset + 各任务完成帧），另附每个相机的 `kind` 与参数清单。

同一个 `preview_manifest.json` 里还有 `camera_world_poses.by_camera`，记录每个相机在
每个采样帧的**实际世界位姿**（`pos` / `forward` / `up`）。这是唯一能看到相机到底落在场景
哪里的地方，因为 YAML 里的 `eye`/`target` 都是**局部位移**，不是世界坐标：

```
world_eye    = body_world_pos + R_body @ eye
world_target = body_world_pos + R_body @ target
```

对比一下就很清楚（`partial-v2` episode 0）：

| 相机 | frame 0 的 pos | frame 369 的 pos | 说明 |
|---|---|---|---|
| `global_free_default` | [-0.848, -1.182, 3.262] | 同一个值 | 自由相机，世界位姿固定 |
| `global_left_cap` | [-1.224, -0.476, 1.799] | 同一个值 | 场景内置相机，世界位姿固定 |
| `wrist` | [-0.456, -0.210, 2.008] | [-0.292, 0.111, 2.409] | **每帧都变**，因为是法兰位姿 + 局部偏移 |

所以三种 `kind` 的"起点"来源完全不同：

| kind | 起点（位置） | 朝向 |
|---|---|---|
| `free` | 不是直接给的：由 `lookat` + `distance/azimuth/elevation` 反算 | 指向 `lookat` |
| `fixed` | 写死在场景 XML 的 `<camera>` 里，YAML 只给 `name` | 同 XML |
| `attached` | **`body` 的原点**（会随机器人动），`eye` 是在该 body 系里的偏移 | `eye → target`，滚转由 `up` 定 |

`attached` 的 `eye` 和 `target` **都是点**：一个是相机位置，一个是注视点（这和 `lookat` 是同一个意思，
只是换了坐标系）。要让相机固定在某个绝对位置，就该用 `free` 或 `fixed`。

### attached 相机只有三个参数

一个 `attached` 相机由**位置(3) + 注视点(3) + 滚转角(1)** 完全确定，没有别的：

| 参数 | 含义 |
|---|---|
| `site` / `body` | 基准坐标系。二选一，见下一节——**末端相机要用 `site`** |
| `eye` | `[x, y, z]` 相机位置，在该坐标系的局部坐标里 |
| `target` | `[x, y, z]` 注视点，同一个坐标系 |
| `roll` | 绕视线自转的角度（度），可省略，默认 0 |

```yaml
  wrist:
    kind: attached
    site: end_effector         # 末端坐标系，不是 body: panda0_link7
    eye: [0.0, 0.0, -0.21]
    target: [0.0, 0.0, 0.14]
    roll: 45.0
    reference_camera: left_cap
```

三个要点：

1. **只有方向 `target - eye` 有意义**，注视点落在同一条射线上的哪个位置都等价。
2. **`roll = 0` 表示"让该坐标系的 `+y` 在画面里朝上"**（在视线允许的范围内尽量）。
   这是唯一需要额外约定的地方：当视线几乎沿着该系的 `±y` 时 `+y` 作参考会退化，
   此时自动改用 `+z` 作参考，不会报错。
   `roll` 正值让画面内容**逆时针**旋转——实测 `roll=+90` 与"把 0 度图逆时针转 90°"的
   MSE 仅 **0.01**；而且它是**纯自转**，不改位置、不改视线。
3. `reference_camera` 只用于初始化视锥，不影响最终外参。

### 为什么末端相机必须用 `site: end_effector`

这是因为 `panda0_link7` 的 x/y 轴**和夹爪自己的轴差了 45°**：
手指是沿 link7 的 `x = y` **对角线**滑动的。实测滑动轴
在 link7 系里是 `[±0.7071, ±0.7071, 0]`，在对角线方向上。

模型自带一个标准末端坐标系：

```
site end_effector
  body      = panda0_link7
  site_pos  = [0, 0, 0.21]                 ← 两指之间的 TCP
  site_quat = [0.92388, 0, 0, -0.382683]   ← 绕 z 轴 -45°
```

也就是说两系之间只差：**沿 +z 平移 21 cm，再绕 z 转 −45°**。在 `end_effector` 系里
手指滑动轴正好变成 `[0, ±1, 0]`，于是语义终于对了：

| 想问的事 | 在 `end_effector` 系里 | 在 `panda0_link7` 系里 |
|---|---|---|
| 相机在夹爪中线上吗 | `eye = [0, 0, z]` | 也是 `eye=[0,0,z]`，但… |
| **"y 分量为 0"等于在横向中线上吗** | **是**（y 就是张开方向） | **不是**：x/y 都被转了 45°，纯 y 偏移其实是沿对角线偏 |
| 两指连线水平/竖直 | `roll = ±90` / `roll = 0` | 要写 `roll = 45` / `roll = −45` 这种"借位"值 |

具体地说，`eye = [0.1, 0, 0]`（link7 系）换算到夹爪系是
`[0.0707, 0.0707, −0.21]`——**x 和 y 各偏一半**，沿对角线。所以它在画面里
x、y 两个方向都偏，这不是 `roll` 造成的。

换算公式（`v` 为任一向量，`Rrel = R_link7^T @ R_end_effector`）：

```
v_ee    = Rrel^T @ (v_link7 - [0, 0, 0.21])
roll_ee ≈ roll_link7 + 45        # 视线沿夹爪轴时严格成立；
                                 # 视线一偏，roll 参考要先投影到垂直视线的平面，
                                 # 于是差值会漂零点几度（例如偏 5.7° 时是 44.86°）
```

`configs/cameras_candidates.yaml` 里 `wrist_aim_diag_*` 两个条目的 roll 就是
按这个精确解出来的（46.457 / 43.543），效果是**与原 link7 写法逐像素等价**
（实测平均绝对差 0.0000、差异像素 0）。

### 位置和朝向必须一起调

`target` 是该坐标系里的一个**点**，所以你把 `eye` 往旁边挪一点、`target` 不动，
**视线就跟着转了**。这两组参数是耦合的，只扫 `eye` 扫不出完整空间。

`scripts/sweep_camera.py` 会把**位置 × 注视点 × roll 的笛卡尔积**全部渲染出来。
只传你想扫的轴，没传的轴自动固定成当前配置的值：

```bash
# 后退多少（位置）× 看多远/看哪（注视点）：3 组
python scripts/sweep_camera.py --camera wrist --eye-z -0.51 -0.41 -0.21

# 注视点往两个方向偏，位置不动
python scripts/sweep_camera.py --camera wrist --eye-z -0.41 \
    --target-x 0.0 0.18 --target-y 0.0 0.18

# 只扫滚转
python scripts/sweep_camera.py --camera wrist --roll -90 -45 0 45 90
```

输出：

* `previews/camera_sweep/sweep_<camera>.png` — 每行一组参数、每列一个关键时刻，带标注；
* 终端先打印解析出的基准坐标系与各轴取值，再打印每组的 `motion`（帧间变化），
  并把一组参数输出成可粘贴的 YAML；
* 同目录的 `.json` 里有全部组合的数值，便于脚本化筛选。

`motion` 是帧间像素变化（接近 0 说明相机对着不动的墙，对策略没信息量）。

**这里刻意没有"质量分"。** 早期版本用"画面中央 40% 的近黑像素占比"当遮挡率、并据此把参数
排序，那是错的，已经删除：它量到的其实主要是**相机在看什么表面**（深色花岗岩台面 vs 亮色墙面），
而且腕部相机本来就**应该**把夹爪拍进画面，把"中央被夹爪占据"当缺点是把方向搞反了。
判断画面好不好，看图；判断相机在哪、瞄哪，看位姿图。

### 实测取舍（`end_effector` 系）

**先说结论：不要用任何"打分"来挑相机。** 早期版本用一个"遮挡率"指标给参数排序，
那个指标是错的（见上一节），本节原先基于它得出的结论（"往 +y 偏更便宜"、
"tilt 很贵"等等）**一并撤回**——那些数字量的是画面亮度，不是遮挡。

现在只保留一条**可靠的几何规则**，它不依赖任何图像统计：

| 规则 | 依据 |
|---|---|
| `eye` 的 z 要 <= 约 −0.18 | 手掌网格在 `end_effector` 系里占据 z ≈ −0.18 ~ +0.03；相机进到里面，画面正中会渲染出网格的**黑色内表面** |
| `eye` 的 x / y 为 0 时相机在夹爪中线上 | 在 `end_effector` 系里 x 跨过两指、y 沿两指张开方向 |
| `eye` 偏离中线（x/y 非零）= 侧视 | 能斜着看，但夹爪会更明显地出现在画面里 |

`target` 只有方向有意义（沿同一条射线移动注视点，渲染结果逐像素相同），
`roll` 是纯自转、只转画面。这两条都有单元测试固定。

挑参数的流程就是**看图**：

```bash
python scripts/sweep_camera.py --camera wrist --eye-z -0.51 -0.41 -0.31 -0.21
# 看 sweep_wrist.png（第一人称，判断"夹爪靠近物体时目标还在不在画面里"）
# 看 sweep_wrist_poses.png（位姿图，判断相机在哪、瞄哪）
```

如果想真正量化"夹爪遮了多少画面"，唯一诚实的做法是
**把夹爪的 geom 隐藏后渲染求差**，算出夹爪实际覆盖的像素比例——但这仍然只是个数字，
判断标准还得看任务需不需要看得见夹爪后面的东西。

### 换基准坐标系也可以，但要重调 `eye` / `target`

`site` 和 `body` 都支持（二选一，同时写会报错）。除了 `end_effector`，
`panda0_link7`、`panda0_leftfinger`、`panda0_rightfinger` 等也可以作基准，
但**每个坐标系的局部轴不同，换了之后同样的数字会给出完全不同的画面**。
实测各 body 相对 `panda0_link7`：

| body | 原点（link7 系） | 其 `+z` 在 link7 系中的方向 |
|---|---|---|
| `panda0_link5` | [0.064, 0.061, 0.0] | [-0.548, -0.522, 0.654] |
| `panda0_link6` | [0.064, 0.061, 0.0] | [0.689, -0.725, 0.001] |
| `panda0_link7` | [0, 0, 0] | [0, 0, 1] |
| `panda0_leftfinger` | [0.034, 0.034, 0.165] | [0, 0, 1] |
| `panda0_rightfinger` | [-0.027, -0.027, 0.165] | [0, 0, 1] |

注意 `link6` 的 `+z` 与 `link7` 的 `+z` 几乎垂直——上面"eye 的 z 必须 <= −0.18"
这条规则在 `link6` 系里完全不适用，必须用 `scripts/sweep_camera.py` 重新扫。

### 位姿图：把相机在哪、瞄哪画出来

扫描脚本除了逐帧对比图，还会**额外生成一张位姿图** `sweep_<camera>_poses.png`：
用第三方视角（自动挑配置里第一个 `free`/`fixed` 相机，一般是 `global_*`）把每组参数的
**起点 `eye` 和终点 `target` 画成红色小球**，中间连一条白线表示视线。

```bash
python scripts/sweep_camera.py --camera wrist \
  --eye-z 0 --eye-x 0.0 0.1 --target-x 0.04 --target-z 0.3 0.6 --roll 0
# 产物：
#   sweep_wrist.png         逐帧第一人称对比
#   sweep_wrist_poses.png   位姿图（红球 = eye / target）
#   sweep_wrist.json        全部数值
```

两点说明：

* 球和杆是把 `eye` / `target` 投影到图像坐标后用 PIL 画的**二维标注**，不参与深度遮挡，
  所以永远不会被手臂挡住。图像内容本身仍是 MuJoCo 的正常渲染。
  （早期版本试过往 MuJoCo 场景里注入调试图元，那条路在当前的 Python 绑定下会写坏
  `mjvScene`，随后段错误，已经废弃。）
* 每块左上角有一行**黄色标签**，说明这块对应哪组参数；标签画在拼好的整张图上，
  格子宽度会按文字宽度撑开，所以不会被裁掉。除此之外图上不画任何文字。

相关开关：`--context-camera`（默认自动，传 `none` 关闭）、`--pose-zoom`、`--pose-margin`、
`--pose-radius`（红球半径，米；球小的时候会埋在手臂里看不见，可以调大）。

### 世界位姿在哪看（manifest）

`eye` / `target` 都是**局部位移**，不是世界坐标：

```
world_eye    = frame_world_pos + R_frame @ eye
world_target = frame_world_pos + R_frame @ target
```

`scripts/preview_cameras.py` 会把每个相机在每个采样帧的**实际世界位姿**
（`pos` / `forward` / `up`）写进 `preview_manifest.json` 的 `camera_world_poses`。
对比一下就很清楚（`partial-v2` episode 0）：

| 相机 | frame 0 的 pos | frame 369 的 pos | 说明 |
|---|---|---|---|
| `global_free_default` | [-0.848, -1.182, 3.262] | 同一个值 | 自由相机，世界位姿固定 |
| `global_left_cap` | [-1.224, -0.476, 1.799] | 同一个值 | 场景内置相机，世界位姿固定 |
| `wrist` | [-0.456, -0.210, 2.008] | [-0.292, 0.111, 2.409] | **每帧都变**，因为是末端位姿 + 局部偏移 |

所以三种 `kind` 的"起点"来源完全不同：

| kind | 起点（位置） | 朝向 |
|---|---|---|
| `free` | 不直接给：由 `lookat` + `distance/azimuth/elevation` 反算 | 指向 `lookat` |
| `fixed` | 写死在场景 XML 的 `<camera>` 里，YAML 只给 `name` | 同 XML |
| `attached` | **`site`/`body` 的原点**（会随机器人动），`eye` 是在该系里的偏移 | `eye → target`，滚转由 `roll` 定 |

要让相机固定在某个绝对位置，就该用 `free` 或 `fixed`。

⚠️ **一个绕不开的限制**：`roll` 是固定在局部坐标系里的常量，而 `panda0_link7` 会随手腕转动，
所以手腕一滚画面的地平线就跟着滚——不存在静态配置能让画面始终"水平"。
如果你更看重画面稳定，可以考虑挂到 `panda0_link6`（不跟夹爪最后的 roll 转），
或者让参考方向每帧从**世界重力方向**算出来（代价是相机不再是刚性附着在手上）。

## 4. 转换成 LeRobot v3

```bash
# 冒烟：先转 1 条，确认图像、prompt、meta 都对
kitchen-to-lerobot \
  --dataset-id D4RL/kitchen/complete-v2 \
  --repo-id local/fk_smoke \
  --output-root data/lerobot/fk_smoke \
  --max-episodes 1 --width 128 --height 128

# 正式：partial-v2 全量 + 前缀展开（1/2/3/4 任务指令）
kitchen-to-lerobot \
  --dataset-id D4RL/kitchen/partial-v2 \
  --repo-id local/fk_partial \
  --output-root data/lerobot/fk_partial \
  --emit-prefixes
```

若只验证固定的前两个任务一次连续完成，不混入其他 prompt，可改为：

```bash
kitchen-to-lerobot \
  --dataset-id D4RL/kitchen/complete-v2 \
  --repo-id local/fk_complete_two_task \
  --output-root data/lerobot/fk_complete_two_task \
  --prefix-length 2
```

这会为每条源轨迹只写一个 `microwave → kettle` episode；不能与
`--emit-prefixes` 同时使用。

要点：

* **`--emit-prefixes`**：一条完成 4 个任务的源轨迹会展开成 4 条 LeRobot episode
  （指令分别是 1、2、3、4 个任务），这是让模型学会**单任务**和**短序列**指令的关键。
  代价是重叠前缀会重复存储，且靠前的任务被重复加权（数据量约 ×2.6）。
* **渲染复用**：同一条源轨迹的多个前缀只渲染一次（实测 2 条源轨迹 1570 帧 → 393 帧渲染）。
  用 `--no-frame-cache` 可以关掉。
* **退化样本默认已过滤**：`--min-episode-steps 30`、`--min-first-completion-frame 1`
  会丢掉 18 条"1 步且开始即完成"的演示尾巴（见 [数据集与Prompt.md §5.1](数据集与Prompt.md)）。
* **留出未见顺序**（做"是否真的听指令"实验时很有用，可重复传参）：

  ```bash
  kitchen-to-lerobot --dataset-id D4RL/kitchen/partial-v2 \
    --repo-id local/fk_holdout --output-root data/lerobot/fk_holdout \
    --emit-prefixes \
    --exclude-sequence "kettle,light switch,slide cabinet,hinge cabinet"
  ```

* **prompt 风格**：`--prompt-style natural`（默认）或 `compact`。
  风格会记进 `conversion_manifest.json` 的 `prompt_style`，评测时要传一致的 `--prompt-style`。
* **分片并行**：`--episode-offset` + `--episode-stride` 可以把 episode 切成若干份，
  多进程各写一个数据集再用 `lerobot.datasets.aggregate.aggregate_datasets` 合并。
  渲染是唯一瓶颈（本机软件 EGL 约 165 ms/相机/帧，GPU 上会快很多）。

每次转换都会写 `conversion_manifest.json`，含相机名、分辨率、配置哈希、
源顺序统计、prompt→帧数统计，便于复现。


先跑这一步：它是 1 个 batch 的前向 + 反向 + 优化器步，用于在长跑之前抓出
相机键不匹配、state/action 形状不对、显存不够等问题。通过会打印 `SMOLVLA_TRAIN_STEP_OK`
并给出显存峰值；OOM 会提示改用 `--resize 224` 或 `--batch-size 1`。

### 5.2 正式训练

```bash
scripts/train_smolvla.sh \
  "$(ls -d ~/.cache/huggingface/hub/models--lerobot--smolvla_base/snapshots/*)" \
  "$PWD/data/lerobot/fk_partial" \
  outputs/train/fk_smolvla_v1
```

脚本可被环境变量覆盖，例如：

```bash
STEPS=20000 BATCH_SIZE=2 NUM_WORKERS=2 RESIZE=256 \
  scripts/train_smolvla.sh <MODEL_PATH> <DATASET_ROOT> <OUTPUT_DIR>

DRY_RUN=1 scripts/train_smolvla.sh <MODEL_PATH> <DATASET_ROOT>   # 只打印命令
```

默认配置与理由：

| 参数 | 默认 | 理由 |
|---|---|---|
| `--policy.input_features=null` | **必须** | 见 §5.3 |
| `[resize_imgs_with_padding]` | `[256,256]` | 基础配置是 512×512；我们的帧就是 256，降到 256 让 SigLIP token 数降 4×，显存占用显著下降 |
| `--policy.use_amp` | `false` | LeRobot 0.6.1 的 AMP 会给 BF16 梯度错误套用 FP16 GradScaler；VLM 权重本身仍以 BF16 加载 |
| `--policy.freeze_vision_encoder` | `true` | 小数据量先只训 action expert（可训练参数 100M / 总 450M） |
| `--policy.train_expert_only` | `true` | 同上。数据量很大或欠拟合时再用 `FREEZE_VISION_ENCODER=false TRAIN_EXPERT_ONLY=false` 解冻全部 |
| `--policy.optimizer_lr` | 1e-4（基础配置） | 可用 `LR=` 覆盖 |
| `--dataset.eval_split` | 0.05（仅当 `EVAL_STEPS>0`） | 按 **episode** 切分，顺序不会在训练/验证间泄漏 |
| `--execution_horizon`（评测） | 10 | 训练无关，见 §6 |

LeRobot 0.6.1 **没有梯度累积**参数；要更大有效 batch 就调 `--batch_size`，或用
`accelerate launch` 多卡。

### 5.3 为什么 `--policy.input_features=null` 是必须的

smolvla_base 在 6-DoF SO-100/SO-101 上预训练，它的 `config.json` 里 `input_features`
是**非空**的：`observation.state`（6 维）+ `observation.images.camera1/2/3`。

LeRobot 的 `make_policy()` 只在 `input_features` 为空时才从数据集推断：

```python
if not cfg.input_features:
    cfg.input_features = {k: v for k, v in features.items() if k not in cfg.output_features}
```

不加这个参数，模型会继续期待 `camera1/2/3` 和 6 维 state，第一次前向就会报
`All image features are missing from the batch`（state 归一化器形状也会错）。

传 `null` 后 LeRobot 从我们的数据集重新推断特征，于是：

* `observation.state` 变成 18 维机器人本体状态（9 维 qpos + 9 维 qvel；会 padding 到
  `max_state_dim=32`，`state_proj` 是 `Linear(32, hidden)`，与预训练权重形状无关，
  所以 18 维可以直接加载）；
* 相机键名变成我们自己的（`global` / `wrist` / 任意名字）；
* `output_features` 本来就会被无条件覆盖成数据集的 9 维 action。

已实测：`outputs/smoke_train/checkpoints/last/pretrained_model/config.json` 里的
`input_features` 正是 `observation.images.global` + `observation.images.wrist` + 18 维 state。

### 5.4 显存不够时

按顺序尝试：`RESIZE=224` → `BATCH_SIZE=2` → `BATCH_SIZE=1`；
再不行就 `FREEZE_VISION_ENCODER=true TRAIN_EXPERT_ONLY=true`（默认已是）。
缩短总步数时同步改 `--policy.scheduler_decay_steps`（脚本里 `STEPS` 与它保持一致）。

## 6. 闭环评测

```bash
kitchen-eval \
  --policy-path outputs/train/fk_smolvla_v1/checkpoints/last/pretrained_model \
  --tasks microwave kettle --episodes 20 --seed 0 --record
```

* 成功与否由**环境自己的 goal 阈值**判定，不由模型声称；
* `--execution-horizon 10`（默认）：每预测 50 步的 chunk 只执行前 10 步就重新规划。
  基础配置是 50（等于整段开环），在 280 步的 episode 里反应太慢。
  这是**纯推理期**参数，训练 loss 始终覆盖完整 chunk，改动不会让 checkpoint 失效；
* 报告写在 `--output-dir`，文件名带上任务序列，便于对比不同指令；
* **一个 seed 赋值给两路噪声**。`--seed S --episodes N` 让第 i 集拿到 `S+i`，这个值被同时赋给：

  | 噪声 | 由谁播种 | 作用 |
  |---|---|---|
  | 环境**观测噪声** | `env.reset(seed=S+i)`（numpy） | 加在 18 维机器人状态上；**还经控制器反馈**，所以也扰动轨迹 |
  | 策略 **FM 采样噪声** | `LoadedPolicy.assign_seed(S+i)`（torch 生成器） | 决定每次推理抽到的 x₁，即动作 |

  所以同一个 `(seed, 指令)` 永远得到同一条 episode，不同指令之间可比；而**不同集之间两路噪声都不同**，
  一轮 20 集就已经在两种噪声上做了平均。启动时会打印这组配置。

  参考值：`--robot-noise-ratio 0.01` 是环境自带的默认幅度（单关节 ±0.001 rad）。
  它是**观测噪声，不是初态扰动**——`reset_model()` 给的初态与 seed 无关，实测 30 维 qpos 逐位相同。
  物体的观测噪声（`observation` 的 18:59 维）永远不会进策略状态，所以没有暴露成参数。

自定义措辞（例如测一个训练时没见过的说法）：

```bash
kitchen-eval --policy-path ... --tasks microwave --instruction "Please open the microwave."
```

## 7. 指令敏感性探针（回答"它到底有没有在听指令"）

成功率会被很多因素混淆（策略可能只是记住了轨迹）。更直接的判据是：
**同一个初始状态，给不同指令，动作是否真的不同**。

```bash
# 正确顺序 vs 反序，同一批 seed
kitchen-instruction-probe \
  --policy-path outputs/train/fk_smolvla_v1/checkpoints/last/pretrained_model \
  --tasks-a microwave,kettle --reverse-of-a \
  --seeds 0 1 2 3 4 --steps 120
```

它会用同一个 `seed` 分别跑指令 A 和 B，然后报告：

* `seeds_with_identical_rollouts`：动作逐帧完全相同的 seed 数。
  **如果这个数等于 seed 总数，说明模型在这个配置下完全忽略语言输入**；
* `mean_changed_step_fraction`、`mean_action_l2`：动作轨迹的发散程度；
* `first_task_matches_instruction_a_rate` / `_b_rate`：第一个完成的任务是否等于指令里的第一个任务。

环境在这里用"全部 7 个任务"作为 goal 集合，所以能看到模型**实际**去动了哪个物体，
而不只是它是否完成了被指定的那个。

### 为什么两臂必须共享同一个 seed

SmolVLA 的 flow matching 从标准正态噪声出发积分得到动作；动作依赖这个噪声。
所以只要两臂的噪声不同，"动作不一样"就完全无法证明"模型在听指令"——
一个**完全忽略文本**的策略也会因为噪声不同而给出不同动作。

探针因此把**同一个 seed 赋给 A、B 两臂**（`--seeds` 里的每个值都同时赋给环境观测噪声和策略采样噪声）。
因为 `LoadedPolicy.assign_seed` 把该 seed 字面赋值给生成器，两臂的第 k 次重规划抽到的是同一个数，
唯一的差别只剩语言输入。这个机制已自检通过：

| 情况 | 每步动作 L2 | 结论 |
|---|---|---|
| A=B（同一句指令） | **0.0000**，逐帧完全一致 | 噪声流确实受控，比较有效 |
| A≠B（微波炉 vs 灯开关） | 0.6765，100% 的步都不同 | 差异确实来自语言 |

如果 A=B 时 L2 不为 0，说明两臂的噪声没有对齐，此时任何"对语言敏感"的结论都不成立。
`tests/test_runtime.py` 里
`test_assign_seed_replays_identical_noise_for_the_same_seed` 与
`test_env_observation_noise_realisation_follows_the_episode_seed` 就是在守这条性质。

## 8. 小规模验证链路（建议的第一轮）

先用 `complete-v2`（19 条、**单一顺序**、起始状态完全一致）把整条链路走通，
确认模型能在过拟合级别上学会"照指令执行"，再上 `partial-v2` 全量。
`complete-v2` 的固定顺序是 `microwave → kettle → light switch → slide cabinet`。

```bash
# ① 转一份小数据集：19 条源轨迹 -> 76 条 episode（4 种前缀指令），约 1.6 万帧
kitchen-to-lerobot \
  --dataset-id D4RL/kitchen/complete-v2 \
  --repo-id local/fk_complete \
  --output-root data/lerobot/fk_complete \
  --emit-prefixes

# ② 体检：确认 4 个 prompt、相机键、帧数都对
kitchen-dataset-report --dataset-id D4RL/kitchen/complete-v2 \
  --lerobot-root data/lerobot/fk_complete --top 3

# ③ 单步显存/接线体检
python scripts/smoke_train_step.py --dataset-root data/lerobot/fk_complete \
  --checkpoint "$(ls -d ~/.cache/huggingface/hub/models--lerobot--smolvla_base/snapshots/*)" \
  --device cuda --resize 256

# ④ 训练。数据量小，步数可以大一些让它记住这个序列
STEPS=8000 BATCH_SIZE=8 EVAL_STEPS=500 \
  scripts/train_smolvla.sh \
  "$(ls -d ~/.cache/huggingface/hub/models--lerobot--smolvla_base/snapshots/*)" \
  "$PWD/data/lerobot/fk_complete" outputs/train/fk_complete_v1

# ⑤ 闭环评测：单任务 → 两任务 → 完整四任务，看成功率是否随长度递减
for t in "microwave" "microwave kettle" "microwave kettle light switch" \
         "microwave kettle light switch slide cabinet"; do
  kitchen-eval \
    --policy-path outputs/train/fk_complete_v1/checkpoints/last/pretrained_model \
    --tasks $t --episodes 20 --seed 0 --output-dir outputs/eval/fk_complete_v1
done

# ⑥ 指令敏感性：正确顺序 vs 反序（同一初始状态、同一噪声种子）
kitchen-instruction-probe \
  --policy-path outputs/train/fk_complete_v1/checkpoints/last/pretrained_model \
  --tasks-a microwave,kettle --reverse-of-a \
  --seeds 0 1 2 3 4 --steps 120 --device cuda
```

怎么判断这一轮成功了：

* ④ 的第 6 步显存峰值在预算内、`loss` 明显下降（不是卡在 2.0 附近不动）；
* ⑤ 单任务成功率明显高于随机，且"完整四任务"成功率 ≥ "两任务" ≥ 单任务 的量级关系合理
  （如果四任务比单任务还高，通常说明模型在背轨迹而不是听指令）；
* ⑥ 里 `seeds_with_identical_rollouts` **小于** seed 总数，且 `mean_action_l2` 明显大于 0
  ——这直接证明它读到了语言输入。

这一轮**不能**回答"模型能否处理没见过的任务组合"，因为 `complete-v2` 只有一个顺序。
那个问题要用 `partial-v2` 全量 + `--exclude-sequence` 留出来做（见实验矩阵第 4 条）。

## 推荐实验矩阵

1. **专家可复现性**：`kitchen-validate` 确认标签与回放，再抽查几条
   `kitchen-replay --mode actions` 的视频。
2. **见过的完整序列**：按 episode 切训练/测试，同一组合测不同轨迹。
3. **单任务 / 短前缀**：只评估数据里确实出现过的（前缀）指令。
4. **未见重组**：用 `--exclude-sequence` 整条顺序不训练，检验模型是真在听序列还是背轨迹。
5. **指令对照**：`kitchen-instruction-probe` 比较正序/反序/无关目标。
6. **相机消融**：只换 `configs/cameras.yaml` 里的相机再转一次数据集，比较成功率。

## 已知限制

* 演示数据里"没有人说话"，prompt 是**事后标注**的：同一条 episode 的所有帧共用整段序列指令，
  模型必须从图像自行判断"现在该做第几个"。它学的是"指令 → 轨迹"的对应，而不是逐步的语言条件。
* `partial-v2` 的 episode 起始状态各不相同（`complete-v2` 则完全一致），
  所以前缀 ≠ "从 reset 开始做前 k 个任务"。
* 当前版本解决的是"任务名/任务序列 → 指令 → 动作"。
  如果上游选择模块输出的是实例 ID 或图像 mask，需要先定义它到 Kitchen 这 7 个任务的映射，
  不能把内部 ID 直接写进自然语言。
* 单任务和短序列的监督全部来自 `--emit-prefixes` 的前缀展开，是真实执行的前缀，
  不是重新编排的任务顺序。
